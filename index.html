01 / Architecture

The model writes. Scout controls the conditions.

Scout is deliberately more than a prompt wrapped around an LLM. Deterministic code owns query handling, retrieval, state, evidence contracts, tool boundaries and validation. Generative inference is used to produce natural language inside those constraints.

Control turns are cheaper.Greetings, thanks, user-profile updates and other conversational control intents can bypass RAG and use compact fact-free generation packets.
Substantive turns are RAG-first.Relevant local evidence is retrieved before generation. Structured tools may enrich evidence; they are not supposed to replace the primary RAG context.
Failure closes down, not outward.Unsupported generation is rejected, repaired or constrained. Unknown evidence is represented explicitly instead of forcing a confident yes/no answer.
02 / What exists

Current capabilities, not brochure fiction.

These are capabilities present in the integrated Scout code line today. They are recruiter-focused because ProjectHub Recruiter Alpha is the current production application.

RAG.01

Local lexical retrieval

Okapi BM25 retrieves verified fact chunks locally. Conversational follow-ups can fuse literal, alias-expanded and context-rewritten rankings using dependency-free RRF.

CTX.02

Structured conversation state

The backend, not the browser, owns compact session state for topic, projects, job context, comparisons, user name, unresolved references and the latest five turns.

CNT.03

Semantic response contracts

Scout builds intent, fact-state, polarity, required-entity and evidence boundaries before generation so the model is not asked to invent the rules of the answer.

TOOL.04

Allowlisted read-only tools

Current tools search verified portfolio evidence, retrieve projects and profiles, compare projects, find skill evidence, match roles and assemble recruiter briefs. Unknown tools fail closed.

VAL.05

Post-generation grounding

Generated answers are checked for unsupported entities, numbers, tech/project relationships, provenance drift, polarity errors, inflated seniority/expertise and other unsupported claims.

GEN.06

Provider abstraction

Cloudflare Workers AI is the production primary. Ollama is the development/evaluation runtime and a gated fallback architecture. Provider/model selection sits behind an inference router.

OBS.07

Runtime telemetry

Scout can expose safe metadata for prose source, provider/model, calls, token/neuron estimates, latency, repairs, retrieval candidates and selected evidence without exposing raw private knowledge.

OPS.08

Protected release path

master and develop are protected. CI checks builds, retrieval quality, dependencies, knowledge validity, staging isolation, secret patterns and other release invariants.

UX.09

Embeddable frontend

The public chat widget remains vanilla JavaScript and GitHub Pages-friendly. The live analytics area separately uses Vite and Carbon components while keeping the widget lightweight.

03 / Scope

Portable architecture is not the same as a finished portable product.

This is the biggest correction from the original product page. The current deployment is intentionally scoped to Bradley Matera and Scout's own runtime. The generalized commercial layer still has to be extracted and proven.

Implemented now

ProjectHub Recruiter Alpha

Scout currently has a real tenant: a recruiter/portfolio assistant grounded in bundled verified knowledge and purpose-built recruiter evidence tools.

  • Projects, skills, work history, education, certifications and career-goal questions
  • Role matching and project/skill evidence lookup
  • Multi-turn context, referent handling and visitor-name state
  • Runtime/meta questions about Scout itself
  • Grounded yes/no/unknown behavior and adversarial-claim handling
  • Production Cloudflare generation with local retrieval/validation
Productization direction

Customer-neutral Scout Core

The design direction is a reusable engine that works independently of one customer and becomes specialized through swappable knowledge, policy, workflow, tool and extension packages.

  • Make no-knowledge / empty-Scout operation a supported tested mode
  • Separate current Bradley-specific data and assumptions from core orchestration
  • Define validated customer/domain package contracts
  • Generalize tool and workflow extension boundaries beyond recruiter use cases
  • Prove portability with unrelated domains without modifying Scout Core
  • Package deployment, documentation, licensing and commercial support for transferability
04 / Evidence

The eval history includes the failures.

Scout's development record is useful precisely because the flattering numbers were not treated as sacred. When a stricter audit showed the old scorer was accepting semantically wrong answers, those prior scores were explicitly invalidated and the engine/scorer were changed.

1.000

Current documented Recall@6 on the 40-query retrieval golden set. CI independently fails retrieval changes below 0.90.

40-query

Golden retrieval set for BM25/query-understanding regression measurement.

61-request

Local API acceptance harness covering facts, safety, NLP, memory, references, dialogue and unknown-technology behavior.

132-input

Conversation regression described by the current engineering instructions: 126 retained production inputs plus a six-turn repair regression.

Why there is no giant “99.9% accurate” badge here

On August 19, an earlier qualification looked like 114/115 plus a 40/40 focused run under the old scorer. An independent raw-output audit found false positives: closed-world employer denials, future-capability answers with the wrong polarity, incorrect contract states, and technology provenance drift.

The repository then added a strict semantic scorer, re-scored the stored outputs, exposed a much weaker baseline, and used those failures to drive upstream intent, response-contract, recovery and grounding fixes. That is more valuable than preserving a pretty number.

Current rule: benchmark numbers are evidence only when the scorer itself survives review. Production and develop can also differ, so historical metrics are labeled as historical rather than silently presented as current 8B performance.

06 / Development history

Scout did not start where it is now.

The branch and commit history documents an iterative transition from a portfolio chatbot toward a controlled generative engine.

Earlier ProjectHub

Embeddable recruiter/portfolio chatbot

The project began around a browser widget and recruiter knowledge. Over time, more answer logic, provider fallback and analytics accumulated around it.

July 2026

Release engineering became explicit

Staging isolation, CI hardening, deploy rollback/health checks, protected branches, coordinated releases and source-of-truth guardrails were merged into the repository workflow.

August 2026 · local-agent phase

Small-model harness exposed architecture problems

Conversation resolution, response contracts, tool selection, completeness checks and grounding validators grew while qwen2.5 local models were used for development and evaluation.

August 2026 · architecture correction

Deterministic fallback prose was treated as a blocker

Earlier evaluations showed too much user-visible fallback text was being authored by deterministic code. Recovery was reworked toward contracts plus generative output so the engine controls evidence without impersonating the language model.

August 19

Old qualification numbers were invalidated

A stricter audit found semantic false positives in the old scorer. Stored raw responses were re-scored and upstream intent/contract logic became a target instead of merely tweaking prompts.

August 21

RAG-first restoration + runtime transparency

Knowledge prewarming, META routing, plain-text parsing, evidence propagation, safe per-reply telemetry and Scout self-knowledge were repaired and validated in staging.

August 21–22

Cloudflare Llama 3.1 8B Fast qualified and released

Production moved to @cf/meta/llama-3.1-8b-instruct-fast, followed by a RAG-first production release and frontend cache refresh.

Now

Integrated branch is still being hardened

develop contains post-release changes around evidence selection, negative assessment, future/hypothetical role framing and honest UNKNOWN behavior that have not all been promoted to production.

09 / Honest boundaries

What this page is deliberately not claiming.

These limitations are part of the product story because the repository supports them.

Scout is not currently a general-purpose assistant.

The production runtime knowledge explicitly scopes the current app to Bradley's verified professional information and Scout's own runtime.

No-KB Scout is not a shipped mode yet.

Current CI validates recruiter knowledge keys. Empty-knowledge support is a productization requirement to build and test, not something to pretend already exists.

Browser/WebGPU inference is experimental.

The architecture leaves room for it, but production generation is currently Cloudflare Workers AI.

Ollama is not a qualified production primary/fallback by default.

It is the dev/evaluation runtime and the router requires explicit enablement plus qualification before Cloudflare can fall back to it in production.

The Docker target is ahead of the current production deploy method.

Dockerfiles and production-parity testing exist, while repository release documentation still identifies the current SCP-based GCP production deployment as a legacy path to replace.

Commercial pricing is not finalized.

Scout is being engineered toward a transferable product. This page does not invent a mature SaaS tier structure before the portable customer layer exists.
